Every `.xz` asset on the [`data`](https://github.com/x-cmd/cve/releases/tag/data)
GitHub release. All are regenerated by CI every 4 hours when the
underlying `data/*.tsv` changes.

## URL pattern

Every asset follows the same shape:

```
https://github.com/x-cmd/cve/releases/download/data/<name>
```

with `Accept: application/x-xz` implicit (curl / `xz -dc` handles it
transparently).

## How release asset updates work

The CI pipeline (`release.yml`) compares each `data/*.tsv` against
the asset currently published on the `data` release:

1. Download the latest `cve-all.tar.xz` from `data`.
2. Untar it to `/tmp/prev_data/`.
3. For each `data/*.tsv`, run `cmp -s` against
   `/tmp/prev_data/<basename>`.
4. If different, `xz -9 -k` the file to `release/<name>.xz`.
5. Repack `cve-all.tar.xz` if **any** year changed.
6. Upload only changed files via `gh release upload data ... --clobber`.

A no-op day (no upstream changes, no catalog refresh) skips every
upload step — consumer-cached sha256s stay valid.

## Cache invalidation guidance

If you're caching the assets on your side, revalidate every 4-6
hours. The release tag (`data`) is stable but the asset bytes
under it can change between runs.
